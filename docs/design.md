# scry design

An RSS reader. Its first milestone is also the org's Go app template.

## Stack

- Go, SQLite (`modernc.org/sqlite`), goose, sqlc. Same setup as voodoo.
- HTTP: stdlib `net/http` (`ServeMux` patterns), not echo.
- `html/template` + htmx, voodoo's layout and CSS. Handlers return a full page, or a fragment on `HX-Request`.
- Auth: voodoo session cookie or API key, via `/me`.
- Jobs: Inngest Cloud.

## Template (milestone 1)

scry's first commit is the template: runnable, one example page, CI green, no feed code. After scry ships it moves to its own repo; new projects start from it with `gonew`.

- `cmd/<app>` (`serve`, `migrate`, `doctor`) and `internal/`.
- Env config, `SCRY_` prefix; refuse unsafe prod settings. `SCRY_PROD` defaults to true so a server missing it fails safe; `.env.example` turns it off.
- `SCRY_SITE_URL` is the org website the header tile and footer link to (the design guide: hosts come from env, never code). Same as voodoo's `VOODOO_SITE_URL`: default `http://localhost:4321`, trailing slash trimmed, https required in prod (`CheckServe`, so prod refuses the default). It reaches the layout through `server.New` and `web.New`, no package global. The guide names voodoo's URL `<APP>_AUTH_URL`; scry keeps `SCRY_VOODOO_URL` (see Known issues).
- SQLite: WAL, one writer plus a read pool. Goose migrations in `migrations/`, embedded; sqlc reads them as its schema.
  Writer: `MaxOpenConns(1)`, `_txlock=immediate`. Reader: `mode=ro` (modernc supports it). sqlc output lives in `internal/db` beside `Open`; `doctor` fails on pending migrations.
- HTTP: timeouts, body caps, `CrossOriginProtection`, security headers, `/healthz`.
- voodoo auth middleware, `/me` cached 60 s. The only shared Go code: package `voodooauth` in voodoo's module (`github.com/0xD34DC0D3/voodoo/voodooauth`), stdlib only, plain `net/http` middleware. Everything else is copied.
- Admin is voodoo's `is_admin`, via `RequireAdmin`; no local role table or option.
- Web layout, CSS, vendored htmx. CSP bans inline script and style, so htmx runs with `includeIndicatorStyles` and `allowEval` off (meta tag); no `hx-on`.
- Static files are fingerprinted (`?v=` hash): immutable cache when versioned, 1 h otherwise (fonts, loaded from the CSS).
- Inngest client, `/api/inngest`, `jobs/`.
  Inngest env vars keep the SDK's names (`INNGEST_*`), not `SCRY_`, since the SDK reads them itself; prod requires both keys and refuses `INNGEST_DEV`. `/api/inngest` skips CSRF and voodoo auth (signature-authenticated) and caps bodies at 36 MiB (Inngest's 32 MiB run-state limit plus headroom) instead of 64 KB.
- Pinned tools, CI, govulncheck, `deploy.sh`, `backup.sh`, Caddyfile, systemd.
  Deploy diverges from voodoo's in four ways: `install.sh` runs `scry doctor` (new binary, prod env) after `migrate up` and before installing it; the health check accepts any 2xx because scry's `/healthz` has an empty body; `ci-setup.sh` makes user `deploy-scry` (not `deploy`) so it does not overwrite voodoo's CI key on the shared droplet; the systemd unit leaves outbound HTTPS open (feeds, voodoo, Inngest Cloud). The CI deploy job stays dormant until the repository variable `DEPLOY_HOST` is set. CI checks out voodoo's `main` beside scry for the `../voodoo` replace (see Known issues). `install.sh` reminds the operator to re-sync the Inngest app, which is manual.
- `AGENTS.md`, `docs/design.md`, `docs/initial_milestone.md`.

CI also checks: sqlc output is current, `queries.sql` is ASCII-only (see voodoo `sqlc.yaml`), migrations run up, down, up.

Out: Antfly, MCP, GraphQL, anything app-specific.

## Features

- One feed catalog. Only admins add, pause, or remove feeds, or ask for a sync.
- Users subscribe to feeds and have read/unread state.
- Public view: latest items from all feeds, the catalog, and one feed's items. Excerpts only, linking out. Cached.
- Logged-in view: subscribed items with full HTML. Looking good is a requirement.

## Data

- `feeds(id, url UNIQUE, title, site_url, etag, last_modified, next_fetch_at, fail_count, last_error, disabled_at)`
- `items(id, feed_id, dedup_key, url, title, author, published_at, first_seen_at, UNIQUE(feed_id, dedup_key))`. Kept forever, so an old item is never re-added as new.
- `item_contents(item_id PK, html, excerpt, fetched_at)`. Pruned after 30 days.
- `subscriptions(user_id, feed_id, subscribed_at, read_before_at, after_item_id, PK(user_id, feed_id))`; `after_item_id` (migration `00007`) is the highest `items.id` at subscribe time.
- `item_reads(user_id, item_id, read_at, PK(user_id, item_id))`. Pruned after 30 days.
- Unread: `id` above `after_item_id` (committed after the user subscribed), `first_seen_at` after `read_before_at`, no `item_reads` row, and listable: posted time inside the 30-day window. "Mark all read" moves `read_before_at`. Unread is about arrival (`id`, `first_seen_at`), listing about posting (posted time). (First designed as `first_seen_at` after both `subscribed_at` and `read_before_at`; step 6 replaced `subscribed_at` with the id watermark, see Reading.)
- Lists use an item's posted time: `min(coalesce(published_at, first_seen_at), first_seen_at)` (see Public views). Views show the last 30 days of it. The unread rule still uses `first_seen_at`.
- `PRAGMA foreign_keys=ON` on every connection; deletes cascade.
- `disabled_at` is the one "not fetched" flag: an admin pause and the auto-disable after 10 failures both set it, and the catalog shows either as paused. Resume clears it, resets `fail_count` and `last_error`, and sets `next_fetch_at` to 0 so the feed is due at once (a new feed starts the same way).
- Unknown text is `''`, not NULL; `disabled_at` and `published_at` are nullable. Indexes beyond keys: `items(posted)` and `items(feed_id, posted)` (expression indexes, migration `00006`, which also dropped `items(first_seen_at)`), `items(feed_id, first_seen_at)`, and `subscriptions(feed_id)`, `item_reads(item_id)` for the cascades.
- Migration `00001` (the template's notes table) stays because production applied it; `00002` drops the table and `00003` creates the schema.
- Feed URLs are trimmed, must be absolute http(s) with a host and no userinfo, at most 2048 bytes after encoding, and are stored with scheme and host lowercased. Adding does not fetch; private addresses are refused by the fetcher (step 3), not at add time.

## Sync

- `syncFeed {feed_id}` does everything for one feed. A cron function sends it for each due feed and moves that feed's `next_fetch_at` forward; admins can send it too.
- Concurrency: 1 per feed, 5 overall (the Inngest plan's limit; first planned as about 10).
- Conditional GET, 15 s timeout, 10 MB cap, User-Agent, private addresses refused (redirects included). Fetch and parse outside the transaction, then one short write. Steps return small values (ids, counts), never feed bodies: each Inngest call must finish inside `serve`'s 30 s write timeout and arrive inside its 10 s read timeout.
- Upsert items by `dedup_key`: guid, else link, else hash of title and date. Content is rewritten on every fetch.
- Success, including 304, resets `fail_count`. A failure counts up and backs `next_fetch_at` off, up to 24 h; after 10 the feed is disabled and shown to admins. Inngest retries cover only blips within one run.
- HTML is balanced, then sanitized on the way in (bluemonday `UGCPolicy`, links `nofollow noreferrer`; see Reading); the excerpt is plain text.
- Pruning runs daily in batches (see Step 7 decisions).
- Step 3 decisions: event `scry/feed.sync`; fetch, parse and write run in one step returning a status and item count; a 304 takes the same write with no items. Fetch or parse failures are recorded and end the run normally (no Inngest retry); only database errors fail the step. Both feed writes skip a paused feed, so a pause during the fetch wins. Backoff is computed in the failure UPDATE from the old `fail_count`: 30 min doubling, capped at 24 h; a success sets `next_fetch_at` to now + 1 h. The fetcher checks the dialled IP (covers redirects and DNS rebinding), ignores proxy env vars, allows only http(s) and 5 redirects. Excerpts are 300 runes, taken from the same HTML as the content (content preferred over description). `last_error` keeps 500 bytes.
- Step 4 decisions: cron `schedule-feeds` runs every 10 min and claims at most 100 due feeds (`next_fetch_at <= now`, not disabled, oldest first). A feed is at most 10 min late, an idle tick is one cheap step, and 100 syncs drain in at most 5 min at 5 concurrent 15 s fetches; any excess waits a tick. The claim is one `UPDATE ... WHERE id IN (SELECT ... LIMIT) RETURNING id` in its own step that moves `next_fetch_at` to now + 1 h and returns the ids; a second step sends the events in one `step.SendMany`. A claim retried after its UPDATE committed finds nothing, so it never double-sends; those events are lost and the feeds come due again in 1 h (no outbox). Event IDs are `scry-feed-sync-<feed id>-<claimed next_fetch_at>`, so a retried send is deduplicated by Inngest and the next claim gets a new ID. `sync-feed` has step concurrency 1 keyed on `event.data.feed_id` plus 5 overall, the Inngest plan's limit (Inngest refused the first sync with 10; it is one step, so that covers the run); extra runs queue. `FeedFailed` sets `disabled_at` in the same UPDATE when the new `fail_count` reaches 10. The admin catalog marks an active feed with failures as "failing"; auto-disabled shows as paused with its `fail_count` and `last_error`, and Resume re-enables it. No index on `next_fetch_at`: the feeds table is tiny.
- Steps 4 and 5 were built in parallel (one git worktree each) at the owner's request, departing from AGENTS.md's milestone order. Step 4 merged first; step 5 was rebased onto it.

## Public views

- Step 5 decisions: routes `/` (latest across feeds), `/feeds` (catalog), `/feeds/{id}` (one feed); signed-out access, no login redirect. Excerpts only, escaped text; item and site URLs go through `html/template`'s URL escaping, so `javascript:` becomes `#ZgotmplZ`.
- Cache: a request with no voodoo cookie and no `Authorization` header gets `public, max-age=60`: syncs are hourly at most, so a minute is never meaningfully stale, and it absorbs reloads. A request carrying either gets `private, no-store`, even if voodoo rejected it or was down, since the page may name the user. Every response sets `Vary: HX-Request, Cookie, Authorization`, so a stored anonymous page or fragment is never served to a full-page load or to a browser that just signed in. Errors are `no-store`: error pages name the signed-in user and do not Vary on Cookie.
- Lists: 50 items per page, newest first by `(posted, id)`, with an Older link (`?before=<posted>-<id>`, a keyset cursor on the posted indexes). Without JS it is a plain link to the next page; with htmx it swaps in the next page's items in place, without pushing the URL. A malformed cursor is 400; an unknown feed 404.
- Posted time (changed after step 7, out of milestone order, at the owner's request; departs from the original "lists use `first_seen_at`" rule): lists order, window (30 days) and page by `min(coalesce(published_at, first_seen_at), first_seen_at)`, and the catalog's 30-day count uses the same. With `first_seen_at` alone, adding a feed put its whole backlog on top stamped "now", and a feed resurfacing an old post made it look new. Clamping to `first_seen_at` means a future or bogus date cannot pin an item above newer ones, and an item never appears to be posted after scry saw it. A post published more than 30 days ago is never listed, even when first seen today. Index: expression indexes on `CAST(<that> AS INTEGER)` and `(feed_id, CAST(<that> AS INTEGER))` (migration `00006`), not a stored column, so the rule lives in one place and old rows need no backfill. Queries must spell the expression exactly as the index does and CAST their parameters to INTEGER too: a CAST on one side only (or none on the index, with a CAST parameter, which sqlc needs for an int64 type) makes SQLite convert affinity and scan the whole index. `internal/db/plan_test.go` checks the plans. `items(first_seen_at)` was dropped as unused; `items(feed_id, first_seen_at)` stays for the unread rule. A feed's last post (`GetFeedLastPostAt`, `ListCatalog.last_post_at`) is the max of the same expression, so `items(feed_id, posted)` answers it with one seek to the feed's last index entry instead of aggregating every item the feed ever had.
- Relative times: the item meta line shows posted time as server-rendered relative text ("just now", "5m ago", "3h ago", "yesterday", "4 days ago", then "Nov 3", with the year when not the current one), computed by `ago(t, now, toMinute)` in `public.go` at render time; `<time datetime>` keeps RFC 3339 UTC and `title` the absolute UTC time. No client script (the CSP forbids inline script, and the minute-long cache keeps server text accurate enough). "yesterday" is 24-48 hours ago, not a calendar day: the server does not know the reader's time zone. Dates past a week are UTC dates. `ago` is the only relative-time helper: the catalog's last-post column calls it with `toDay` ("today" instead of minutes and hours), which replaced the catalog's own `shortAgo`; that column now switches to a date after a week instead of two, so both places follow one rule.
- List position: the Older link reads "Showing 100 of 312 · Older". `CountLatestItems` / `CountFeedItems` make one covering pass over the window's posted index range, returning the window total and the items after the page's last item; shown is the difference. Deriving it from the cursor, not a page number or offset in the URL, keeps it right in each htmx fragment (which replaces only its own `<li class="more">`) and on a plain-link page, with no extra parameter to validate. It runs only when there is an Older link; the last page keeps the end marker and no count. The count and the list are separate reads, so a sync landing between them can be off by its new items for that one response; accepted, as it is cosmetic.
- The catalog lists every feed, paused or auto-disabled ones marked paused, with its item count for the last 30 days; it is not paged (admins curate it, so it stays small). Paused feeds' items still appear in the lists until they age out. Failure details stay on the admin page.
- UX pass: the header nav has `aria-label="Main"` and marks the current link `aria-current="page"` (`"true"` on one feed, below `/feeds`). Item titles are h2 (no h1 to h3 skip), underlined only on hover/focus, muted once visited. Lists end with "— end of 30 days —" when there is no Older page, even in an empty Older fragment (items aged out between clicks). The Older link dims while loading (`.htmx-request`, no clicks) and the swapped-in fragment's first item has `autofocus`, which htmx focuses, so keyboard focus is not lost; full pages never autofocus. Empty states link on (`/feeds`, `/`, or `/admin/feeds` for admins). Admins see "Manage feeds →" on `/feeds`; cache-safe because an admin request carries a credential, so `setCache` makes it `private, no-store`, and Vary covers Cookie and Authorization. 404, 400, 413 and 500 render through the layout (`web.Renderer.Error`) as `no-store`; a catch-all `/` pattern covers unknown paths, at the cost of 405s becoming 404s (a `GET /` catch-all would conflict with the method-less `/api/inngest` pattern). Admin: h1 "Manage feeds", `main.wide`, buttons disabled in flight (`hx-disabled-elt="find button"` on each form, since the form is the htmx element), long URLs wrap, `last_error` collapsed in a `<details>`. Under 600px the header is not sticky and the item meta line's links (feed, discussion) get a taller tap target.

Feed display (added between steps 5 and 6, out of milestone order, at the owner's request). Every rule is generic, not Hacker News-specific:

- The item meta line shows the item link's domain (`url.Parse(...).Hostname()`, leading `www.` stripped; empty when unparsable or hostless), computed at render time, so changing the rule needs no migration. It also shows `by <author>` when `items.author` is set, and a "discussion" link when `comments_url` is.
- Link-only summaries are dropped at parse time: link-only content (e.g. "Continue reading") falls back to the description, and when that too has no text outside `<a>` elements (whitespace and `&nbsp;` only), both `item_contents.html` and the excerpt are stored as `''`. Covers HN's lone "Comments", lobste.rs link posts, and "Read more" stubs; a lobste.rs text post keeps its text and link. Exception: HTML with an `<img>` is kept (an image-only comic is not empty). Items already stored keep their old excerpt until their next fetch rewrites it.
- `items.comments_url` (migration `00004`, `TEXT NOT NULL DEFAULT ''`) holds RSS `<comments>`, rewritten on every fetch like the other item fields and read by both public list queries. gofeed v1.5.0 parses `<comments>` only onto `rss.Item`, so `parse.go` wraps `DefaultRSSTranslator`: it runs the default, then copies each item's `Comments` into the universal `Item.Custom` under `:comments` (a leading colon cannot be an XML element name, so no unknown element gofeed keeps there collides). Only absolute http(s) URLs with a host, at most 2048 bytes, are kept; anything else stores `''`. The template puts it in `href` as a plain string (never `template.URL`), so even a bad stored value renders as `#ZgotmplZ`. Atom has no equivalent.
- Step 7 decisions: cron `prune` runs daily at 03:17 UTC. Step `cutoff` records now - 30 days once (Inngest replays the function body per step, so a clock read in the body would drift), then steps `prune-contents-N` and `prune-reads-N` each delete one batch of 500 (`DELETE ... WHERE rowid IN (SELECT rowid ... ORDER BY <time> LIMIT 500)`) and return the count; the loop stops at the first short batch. 500 is a short write on the single Writer (tens of ms even with large html), so syncs wait little and each step is far inside the 30 s write timeout, and it keeps step outputs tiny. Loop of steps, capped at 100 per table (about 201 steps, well under ~1000): a backlog over 50,000 rows per table finishes on the next days' runs, and steady state is a few batches; one looping step was rejected because a crash would lose its progress and its length is bounded only by timing. A retried step after a committed delete just deletes the next batch. Migration `00005` adds `item_contents(fetched_at)` and `item_reads(read_at)`, or every batch would rescan the table. The boundary agrees with the views: both use now - 30 days, views keep posted time `>=` it (posted is never after `first_seen_at`, so that implies `first_seen_at >=` it) and the prune deletes rows strictly older. Why that is safe: `fetched_at` is rewritten on every fetch and is never before `first_seen_at`, so a content row older than the cutoff belongs to an item first seen before it, which the views no longer show (still-fed items keep fresh content). An `item_reads` row is written when a reader marks an item read, after the item was first seen, so `read_at >= first_seen_at`; a row older than the cutoff is for an item outside the window. The unread rule only counts items inside the (posted-time) window, so a pruned read row never turns a visible item unread (the argument is spelled out under Reading; `subscribed_at` became `after_item_id` in step 6, which does not change it). Public lists already `LEFT JOIN item_contents` with `coalesce(excerpt, '')`, so an item without content is listed with an empty excerpt (test `TestPublicItemWithoutContent`). Bookmarks (deferred) will need to exempt their items' contents from the prune.

## Reading

Step 6 decisions:

- Routes, all behind `RequireUser` (user id = voodoo's `id`): `GET /reading` (`?view=all`, `?feed=<id>`, `?before=<posted>-<id>`), `POST /reading/mark-all-read` (form `upto`, optional `feed`, `view`), `POST /reading/items/{id}/read` and `/unread` (form `back`), `POST /feeds/{id}/subscribe` and `/unsubscribe` (form `back`). Subscribe sits under `/feeds/{id}` because it acts on a catalog feed; the reading list is its own page. Code: `internal/server/reading.go`, `views/reading.html`.
- Signed-in `/` stays the public latest page (and its cache rules stay as they are). The header nav gains a first link, "reading", shown only when signed in. Subscribe buttons live in a "Reading" column of `/feeds` and under the feed meta on `/feeds/{id}` (both show the feed's unread count, linking to its reading list); signed out, both pages say "Sign in to subscribe and read full posts" instead. Those pages were already `private, no-store` for any credential, so the per-user button is cache-safe.
- The reading page: h1, then a toolbar (unread count for the page's scope, an Unread | All switch, and "Mark all read", the accent action, hidden when the scope has nothing unread), then the subscribed feeds as chips with per-feed unread counts, then the entries. On a feed's page (`?feed=`) the count is that feed's, not the all-feeds total, and the htmx count updates follow it (item forms post the filter as `feed`). The chips wrap at every width (they first scrolled sideways on phones, which could hide the current one). Unread (the default view) shows only unread items; All shows every item from the last 30 days, read ones collapsed to a quiet row (title, meta, a "Show post" `<details>` with the body, and "Mark unread" when the item has a read row). Unread first, because the list is a to-do; All is one click away and is linked from the "All caught up" state.
- An unread entry is a framed card: feed name eyebrow (left out on a feed's own page) with a small "Mark read" at its right, the title (links out), the meta line, the full HTML in `.prose`, then "Open ↗" and a second "Mark read". Two buttons because a full article is long: the top one is where the reader decides to skip, the bottom one where they finish. A link-only item (empty html: HN, Lobsters, or content pruned) is a compact card with just the title, meta and the two actions on one row. `.prose` resets the app's h1/h2/th styles for feed markup, caps images at 100% width, scrolls `pre` and tables sideways, and frames blockquotes, code and figures in the house style. Table cells never break inside a word (`overflow-wrap: normal`, header cells `nowrap`), so a wide table scrolls instead of squeezing its columns to a letter per line on a phone.
- Marking read is an explicit button, not on open or on scroll: it works without JS, never marks something the reader skimmed past, and needs no script beyond htmx (CSP). htmx swaps the entry for its read row and updates the total and that feed's chip count out of band (`hx-swap-oob` on `#unread-total`, `#unread-feed-<id>`); the read row has "Mark unread" as an undo. Without JS the form posts and gets a 303 back to `back`: the same list, anchored on the next entry in the Unread view (the read one disappears) or on the entry itself in All. `back` must be a local path (`/`, not `//`, no scheme or host, no `\` or newline), else the default (`/reading`, `/feeds/{id}`), so it cannot redirect off-site.
- Mark one read: `INSERT ... SELECT` over a subscribed feed's item, `ON CONFLICT DO NOTHING` (the first read time stays); an item in a feed the user does not follow (or no item) is 404. Mark unread deletes the row; it only matters while `first_seen_at` is above both watermarks, so the button only shows then.
- Mark all read and the race. The page posts `upto`, the highest `items.id` when it was rendered (read before the list, so every item on it is at or below). The update sets each subscription's `read_before_at` to `max(read_before_at, newest first_seen_at among that feed's items with id <= upto)`, limited to `feed` when the page was filtered. Item ids grow in commit order (one writer, rowid = max + 1), so ids up to `upto` are exactly what existed at render; and sync runs one at a time per feed, so anything a later sync added to that feed has a later `first_seen_at` and stays unread. Posting the render time instead would be wrong because `first_seen_at` is the sync's start time: an item from a sync that started before the render but committed after it would be swallowed. A stale `upto` never moves `read_before_at` backwards. The per-feed lookup is `ORDER BY first_seen_at DESC LIMIT 1` over `items_feed_first_seen` with `id <= upto`, which stops at the newest pre-render item instead of scanning the feed's whole (never pruned) history. Test: `TestReadingDone`, `TestMarkAllReadNeverBackwards`.
- Unread counts (total, per feed) and the Unread view are limited to the 30-day window by posted time, like every list, so the count is exactly what the Unread view can show. That keeps the prune safe (Step 7) under the posted-time window: a visible item has posted >= cutoff, posted <= `first_seen_at` (the expression clamps it), so `first_seen_at` >= cutoff, and `fetched_at` and `read_at` are never before `first_seen_at`, so its content and read rows are >= cutoff and the prune, which deletes rows strictly older, cannot touch them. Subscribing stores `after_item_id`, the highest item id at that moment, and only items with a larger id can be unread. Not `subscribed_at`: `first_seen_at` is the sync's start time (before a fetch of up to 15 s), so a sync that started before the subscription and committed after it would have its items counted as old, and the reader would never see them unread. Ids grow in commit order (one writer), so the watermark splits exactly at the subscription; an item that a later sync merely refetches keeps its id and stays old. `subscribed_at` is still stored, for information. Migration `00007` adds the column and backfills existing rows from `subscribed_at` (the highest id first seen by then). A new subscription starts at zero unread and fills on the next sync (the empty state says so); unsubscribing deletes the row, and resubscribing starts over from that moment. Test: `TestSubscribeDuringSync`. Item read rows of an unsubscribed feed are left for the prune.
- Order, window and paging follow the public lists (decided at the rebase onto main's posted-time change, for consistency): newest posted first by `(posted, id)`, 30 days of posted time, `?before=<posted>-<id>`, the expression spelled exactly as the `00006` indexes with CAST parameters; `internal/db/plan_test.go` checks the reading list, the unread count and mark-all-read. A post published days ago but synced now sorts by its date, and is still unread (arrival). 10 entries per page (20 real articles measured about 117,000 px), with the filter kept in the Older link. The Older link has no "Showing N of M": the reading list's total depends on the view and filter and would need its own count query; not worth it yet. `ListReadingItems` picks the page's ids (with unread/marked) in a subquery that sorts and limits, then joins `feeds` and `item_contents` onto those rows, so a page reads only its own html (joining content before the sort read every window item's html: 34 ms vs 1 ms at 9k items of 16 KB). A plain post's `back` keeps the page's `before` cursor, so marking read on an Older page returns to that page (`TestReadingBackKeepsCursor`).
- Cache: every reading response, and the subscribe and item fragments, are `private, no-store` with `Vary: Cookie, Authorization` (plus `HX-Request` from `Render`). The public pages' `setCache` is unchanged; signed in they were already private.
- Security: `item_contents.html` is the only `template.HTML`, and it is trusted because bluemonday's UGC policy sanitized it at ingest. Ingest changes (more in the last bullet): the policy now adds `rel="nofollow noreferrer"` to links (noreferrer implies noopener; belt and braces with `Referrer-Policy: same-origin`), and the HTML is first balanced through `x/net/html` (`internal/jobs/content.go`) because bluemonday keeps stray end tags: a `</div>` or `</li>` in a feed would otherwise close the reading page's own elements around it. The same pass drops every `id` and `name` attribute: the UGC policy keeps `id` (and `name` on `<map>`), so a feed could define `title-<n>`, `item-<n>`, `unread-total` or `reading-panel` and hijack `aria-labelledby`/`aria-describedby`, the no-JS `#item-<n>` return anchor, or an htmx target (bluemonday cannot remove an attribute from a policy, so it is done in the parse; `TestContentNoIDs`). Balancing runs before sanitizing, so the sanitizer has the last word. All three reach existing rows only when their next fetch rewrites the content (a 304 does not).
- CSP: the reading page, and only it, adds `img-src 'self' https:` (`readingContentSecurityPolicy`), because article images live on their authors' hosts and were blocked by `default-src 'self'`. Images are the only embedded resource the UGC policy keeps (no iframe, video, audio, object or style), so nothing else is widened; plain-http images stay blocked. Scripts stay `'self'` only.
- Accessibility: the nav link and the Unread/All switch and chips use `aria-current`; each entry is an `<article>` labelled by its h2 title; per-item buttons carry `aria-describedby` the title, so "Mark read" is not ambiguous out of context; forms use `hx-disabled-elt` and dim while `.htmx-request`; "Mark all read" in a filtered view names the feed to screen readers. Every htmx swap that removes the focused button puts `autofocus` on what replaces it, which htmx focuses: the entry (`tabindex=-1`) after Mark read/unread, the unread count after Mark all read, the new button after Subscribe/Unsubscribe, the first new entry after Older. Full pages never autofocus. Tap targets (switch, chips, buttons, the feed eyebrow link, "Show post") are at least 32 px tall on desktop and 44 px on phones (`--tap`).
- Dates: one rule for public and reading pages, main's: posted time as relative text from `ago` ("3h ago", "yesterday", "4 days ago", then a UTC date), `<time datetime>` in UTC and the absolute UTC time as its title. The reading page first had its own absolute format in the reader's voodoo time zone; it was dropped at the rebase so the two never disagree, and relative text needs no zone except for dates past a week (UTC, as on the public pages).
- Dark mode: reading styles use the theme tokens (`--canvas`, `--surface`, `--ink`, `--muted`, `--rule`, `--accent`), so cards, chips, counts, the Unread/All switch, blockquotes, inline code and tables follow the theme. Text on lime (current chip, "All caught up") is `--on-accent` in both themes. Code blocks keep a fixed dark background (`--code-bg`/`--code-fg`) with a `--rule` border, since an ink block would become a light slab in dark mode. Catalog Subscribe buttons are `.ghost` (one accent action per view) rather than restyled by CSS, so the dark theme's accent-button text rule never lands on a non-accent fill.
- On `/feeds` and a feed's page a subscribed feed shows "subscribed · N unread", a "read →" link to its reading list, and Unsubscribe.
- Reviewed in a browser at 1280 px and 390 px from static renders of the real templates and CSS (Chrome headless), using the live E2E database's stored HTML (Go Blog, Simon Willison, Julia Evans, HN, Lobsters) run through the current ingest pipeline; a live E2E against a built binary covered the htmx and no-JS flows.
- Ingest changes for the reading page (`internal/jobs/content.go`, `prepareHTML`, run before sanitizing): balance tags; drop `id`/`name`; resolve relative `href`, `src` and `cite` against the item's link (else the feed's site link; gofeed has already applied Atom `xml:base`), so the Go Blog's `17years/go17.png` and `/pkg/sync` work, and an in-page `#frag` becomes a link to that section of the original post (its target id is gone); with no base, relative URLs are dropped; add `loading="lazy"` to images (the policy allows that one value), which also keeps images in closed `<details>` from loading; remove the first heading whose text is the item's title (the Go Blog repeats it as an h1) and demote the rest two levels (h1 → h3 … capped at h6), so content sits under the entry's h2 in order. All of it reaches stored rows only when a non-304 fetch rewrites their content; until then old rows keep relative URLs, ids and their own h1/h2 (the CSS styles those too).

## Deferred

- GraphQL (gqlgen), until a non-browser client needs it. Resolvers and htmx handlers would wrap the same code.
- TypeScript template, same shape: env names, deploy scripts, docs, look.
- Bookmarks: `bookmarks(user_id, item_id, created_at)`; pruning keeps their `item_contents`. Bookmarking any URL gives it an `items` row with no feed.
- Image proxy, full-article extraction, OPML, search, user-suggested feeds.
- `voodoo/user.deleted`: delete the user's rows.

## Known issues

- scry uses stdlib `net/http`; voodoo uses echo. Code copied from voodoo's server needs porting, not pasting.
- scry's admin is voodoo's `is_admin`, though voodoo's README says `is_admin` is not an app role. Fine while one person runs everything; per-app roles would need a table.
- Copies made from the template drift apart.
- `go.mod` replaces voodoo with `../voodoo` until voodoo tags a version: builds use whatever voodoo is checked out (CI: voodoo's `main`), so a scry build is not pinned to a voodoo commit.
- `voodooauth` calls voodoo's `/me` once per request carrying an unknown or garbage credential (only positive answers are cached; no format check or request coalescing). One call per request, not amplification; revisit if voodoo sees abuse.
- `backup.sh` does not read `/etc/scry/scry.env`. If `SCRY_DB_PATH` there differs from the default, backups print "nothing to back up" and exit 0 without the healthcheck ping (same as voodoo). Keep the default path.
- Images in articles on the reading page load directly from other sites, which see readers' IP addresses (no image proxy yet; the CSP allows https images only there).
- "Mark all read" can swallow an item in two corner cases: the same feed synced twice within one second (same `first_seen_at` on both sides of the watermark), or the feed holding the newest item removed after the render, so SQLite reuses its id for an item that is then at or below `upto`.
- Feed HTML stored before step 6 keeps stray end tags, `id`/`name` attributes, relative URLs, its own h1/h2 and links without `noreferrer` until its next non-304 fetch rewrites it; a stray end tag can break the layout around that entry, a colliding id can misdirect an aria reference or the no-JS return anchor, and relative images 404 on scry (not a security issue: it is still sanitized).
- The nav shows no unread count; the count is on the reading page, `/feeds` and each feed page.
- Feed boilerplate inside content (the Go Blog's "The Go Blog" heading link, author and date lines) is shown as is; only a heading equal to the title is removed.
- Feeds whose guids change on every fetch produce duplicates.
- Inngest sync is manual from the dashboard: inngestgo v0.16+ refuses unsigned `PUT /api/inngest` unless `INNGEST_ENABLE_UNAUTHED_SYNC` is set. Enabling it would also need `ServeOrigin` pinned to `SCRY_BASE_URL`, or the synced URL comes from the Host header.
- Production has no off-box backups yet (`/etc/scry/backup.env` absent); deploys take a local copy only.
- A failure can be counted twice when Inngest retries the sync step after its write committed (the response was lost); ten such doubles disable a feed early. Resume fixes it.
- Feed URL dedup folds only scheme and host case; `:443`, a trailing dot, `#fragment`, or IDN vs punycode variants store the same feed twice.
- Catalog feed URLs and all their items are public, so a feed whose URL carries a secret token (a private feed) leaks it. Don't add such feeds.
- Excerpts put a space wherever an inline tag was stripped, so `about <em>feeds</em>.` reads "about feeds ." (bluemonday `AddSpaceWhenStrippingTag` cannot tell inline from block tags).
- Hacker News items have no guid, so a repost of the same URL folds into one item (dedup_key falls back to the link).
- The design guide names voodoo's URL `<APP>_AUTH_URL`; scry (and voodoo's integration docs) use `SCRY_VOODOO_URL`. Rename or update the guide.
- Error pages from voodooauth's `RequireUser` / `RequireAdmin` (401/403/503) are still voodoo's plain responses, not the layout.
- `web.StaticHandler` serves a directory listing at `/static/`, and a missing static file is a text/plain 404 cached `public, max-age=3600`.
- Admin pages set no Cache-Control. They need auth and send no validators, so nothing caches them in practice.
